# 設計判断ログ

決めたことを、日付・判断・理由・代案の形で残します。新しいものを上に追記します。
仕様の正は Notion の設計書です。ここには「なぜそうしたか」を短く残します。

### D-004: 開発の進め方は .claude/ のエージェント分担で行う（2026-11-27）
- 状態: 確定
- 判断: architect / developer / tester / reviewer / scheduler の5役と、`/morning` `/plan` `/build` `/status` `/review` `/checkpoint` `/parallel` のコマンドで進める。タスクは `.claude/tasks/` に1タスク1ファイル。
- 理由: 1人開発でも設計・テスト・レビューを飛ばさないため。セッションをまたいで状態を引き継ぐため。
- 代案と見送った理由: 外部のタスク管理ツール → リポジトリ内で完結させたほうがエージェントが読み書きしやすい。

### D-003: タグにはランダムIDのURLだけを書く（2026-11-27）
- 状態: 確定（設計書 v0.1 §4・§5）
- 判断: タグとQRには `https://（ドメイン）/t/（推測できないランダムID）` だけを入れ、書き込み後にロックする。個人情報は書かない。会話はサーバーで中継し、お互いの連絡先は見せない。
- 理由: 拾った人に悪意があっても漏れる情報を最小にするため。
- 代案と見送った理由: 連番ID → 総当たりで他人のタグを探せる。

### D-002: 技術構成は Next.js ＋ Supabase を推奨（2026-11-27）
- 状態: 提案（ユーザー未確定）
- 判断: 画面は Next.js（App Router, TypeScript）、データ・認証・写真は Supabase。通知はメールから始め、LINE は後。
- 理由: 1人で認証・DB・ストレージまで早く作れる。会話・通報のような関係データは Postgres が扱いやすい。
- 代案と見送った理由: Firebase（関係データが扱いにくい）、Cloudflare Workers ＋ D1（認証を自前で組む部分が多い）。
- 要確認: Supabase の東京リージョンと料金。

### D-001: 最初の対象は「持ち物」、配布ルートは学校・イベント（2026-11-27）
- 状態: 確定（かくちゃん）
- 判断: 持ち物から始める。子どもの迷子札はフェーズ2。施設側の落とし物管理は対象外。
- 理由: 子どもに結びつく情報は漏れたときの被害が重く、電話中継や対応体制も要るため。
