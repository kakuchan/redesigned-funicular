### D-012: 安全のしくみ（回数制限・ブロック・通報・写真・保存期間）（2026-11-27）
- 状態: 確定（M5）
- 判断:
  - 回数制限は DB の `rate_limit_hit()`（service_role 専用）で数える。1タグへの新しい連絡は1時間5件、同じ送信元から1時間10件、1会話の拾った人の返信は1時間20件、通報は同じ送信元から1日10件。DB に届かないときは止める側に倒す。
  - 送信元は `x-forwarded-for` の先頭の IP を、秘密の塩（`RATE_LIMIT_SALT`）付き SHA-256 にして使う。生の IP は保存もログ出力もしない。会話に付けたハッシュは7日、回数制限の記録は1日で消す。
  - ブロックは「その持ち物への、その送信元からの連絡」を30日止める。相手には「今は連絡できません」とだけ見せる。
  - 通報は reports テーブルに残し、`REPORT_EMAIL` があれば運営にメールする。運営の対応画面は作らず、Supabase の画面で見る。
  - 写真は1枚、ブラウザで長辺1600px の JPEG に描き直し、サーバーでも APP1〜APP15・コメントを取り除いてから非公開バケット `photos` に保存。持ち主にだけ10分の署名付き URL で見せる。拾った人の画面には出さない。
  - 終わってから（受け取り・ブロック・期限切れ）90日で会話・メッセージ・写真を消す。毎日 `/api/cron/purge`（`CRON_SECRET` 必須、Vercel Cron）。
- 理由: 設計書 §4。小さく始めるので、運営の作業は Supabase の画面で済ませる。
- 注意: `x-forwarded-for` は公開先（Vercel など）が上書きする前提。自前のサーバーで動かすときは、信頼できるプロキシの後ろに置くこと。
- 代案と見送った理由: 外部の回数制限サービス（Upstash など）→ 規模が小さいうちは DB で足りる。サーバーでの画像の描き直し（sharp）→ 依存が重い。ブラウザで描き直し、サーバーではメタデータの除去だけにした。

### D-010: 拾った人の操作はサーバー経由のみ、一時リンクはトークンのハッシュで照合する（2026-11-27）
- 状態: 確定（M3・M4）
- 判断: 拾った人の連絡・閲覧・返信は `finder_*` 関数で行い、実行できるのは service_role（Next.js のサーバー）だけ。公開キーで直接は呼べない。一時リンクは 32 バイトの乱数トークン（`/c/<token>`、7日）で、DB には SHA-256 だけを保存する。同じタグを読み直したときのために、トークンを httpOnly cookie に7日置く。持ち主側は RLS で読み、返信・終了は関数で行う。
- 理由: 回数制限・通報・ブロック（M5）をサーバーで必ず通すため。DB が漏れても一時リンクを再現できないようにするため。
- 代案と見送った理由: 拾った人にもメールアドレスを入れてもらう → 匿名で気軽に送れることを優先（設計書 §3-2）。

### D-011: 通知メールは本文を入れず、送り方を差し替えられるようにする（2026-11-27）
- 状態: 確定（M3）
- 判断: 持ち主への通知は「何が見つかったか・どこにあるか・位置の有無・リンク」だけで、拾った人の本文はメールに入れない。送信は `MAIL_PROVIDER`（resend / mailpit / log）で切り替え、失敗してもメッセージの保存は失敗にしない。宛先のメールアドレスは送る直前に service_role で調べる。
- 理由: 転送や誤送信で会話の内容が広がらないようにするため。本番のメール送信サービスが未決でも開発を進めるため。
- 代案と見送った理由: LINE 通知 → MVP 後（未決事項）。

### D-009: ログインはメールの6桁確認コード、タグの登録と解除は DB 関数で行う（2026-11-27）
- 状態: 確定（M2）
- 判断: Supabase Auth のメール OTP で、メールに届く6桁のコードを入れてログインする（初回も同じ）。タグの登録は `register_tag()`（タグ行をロックし、未登録だけを有効にする）、解除は `release_tag()`（持ち物を消してタグを未登録に戻す。運営が止めたタグは戻さない）。持ち主の一時停止は `items.paused` で、拾った人には「今は使えません」と見せる。持ち物の直接の insert・delete は許さない。
- 理由: ログインリンクは、メールアプリ内のブラウザなど別のブラウザで開くと失敗しやすい。保護者のスマホで確実に通るコード方式にした。登録の競合や状態の食い違いを DB の1か所で防ぐため。
- 代案と見送った理由: マジックリンク → 上の理由。LINE ログイン → MVP 後（未決事項）。
- 補足: ログイン後の戻り先はサイト内のパスだけ。入力途中のメールアドレスは httpOnly の cookie に1時間だけ置く。

### D-008: タグの画面は1つの URL で状態ごとに出し分ける（2026-11-27）
- 状態: 確定（T-004）
- 判断: `/t/[id]` で状態を読み、未登録・有効・停止・見つからないを同じ URL のまま出し分ける（リダイレクトしない）。未登録には持ち主向けの「登録する」（`/register/[id]`、中身は M2）と、拾った人向けの案内を両方出す。拾った人用ページは未ログインのまま公開キーで `get_tag_public()` だけを呼び、cookie は使わない。`/t/*` と `/register/*` は検索エンジンに載せず、リファラーを送らない。
- 理由: 未登録のタグを拾った人が読むこともあるため。タグ ID は「知っている人だけが開ける鍵」なので、外部サイトや検索結果に漏らさない。
- 代案と見送った理由: 未登録なら登録画面へリダイレクト → 拾った人が迷う。
- 補足: 停止中・持ち物のない「有効」は、持ち物の情報を出さない。持ち主の文言は React がそのまま文字として出す（HTML として解釈しない）。

### D-007: タグ ID は 57 文字 × 16 桁、発行は運営のスクリプトで行う（2026-11-27）
- 状態: 確定（T-003）
- 判断: 使う文字は英数字から 0 O 1 l I を除いた 57 文字、長さ 16（約 93 ビット）。`crypto.getRandomValues` を使い、偏りが出る値は捨てる。発行は `npm run tags:issue -- --lot ... --count ... --base-url ...` で、secret key（service_role）を使って `tags` に登録し、`id,url,lot` だけの CSV を出す。1回の上限は 10,000 件。
- 理由: 台紙に ID の一部を印字するので読み間違いを減らす。総当たりで他人のタグを探せない長さにする。個人情報を CSV に含めない。
- 代案と見送った理由: UUID（36 文字）→ URL が長く NFC の容量と QR の細かさに響く。DB 側で ID を作る → 乱数の質と文字種をアプリ側のテストで確かめにくい。
- 補足: `--base-url` は本番ドメインが決まるまで仮。タグに書き込む前に必ず本番のドメインで発行する（未決事項「サービス名とドメイン」）。

### D-006: 拾った人には関数だけを開け、テーブルは閉じる（2026-11-27）
- 状態: 確定（T-002）
- 判断: 未ログインの利用者には tags / items の読み取り権限を与えず、`get_tag_public(id)` だけを実行させる。返すのは状態と、有効なときだけ持ち物の名前・一言・紛失モード。停止中は状態だけ、存在しない ID は 0 行。持ち主は自分の持ち物の名前・一言・紛失モードだけを直せ（列単位の権限）、tag_id / owner_id は変えられない。持ち物の作成（タグの登録）は直接 insert させず、M2 で関数として用意する。持ち主が退会すると持ち物は消え、タグは残る。
- 理由: RLS の書き漏れで持ち主の情報が出るのを防ぐため、出してよい列を関数の戻り値で固定する。登録時に「未登録のタグだけを有効にする」処理を1か所にまとめるため。
- 代案と見送った理由: 拾った人用のビュー → ビューの権限と RLS の組み合わせが分かりにくい。停止中を 0 行にする → 拾った人に「このタグは使えません」と案内できない（ID は推測できないので、存在が分かっても困らない）。
- 注意: 生成される型では `get_tag_public` の戻り値が null にならない扱いになるが、未登録・停止中は null が返る。呼ぶ側で null を考慮する。

### D-005: 雛形の細かい選択（2026-11-27）
- 状態: 確定（T-001）
- 判断: Node.js 22 以上、Next.js 16（create-next-app の既定のまま `cacheComponents` 有効）。Supabase の鍵は新しい名前の公開キー `NEXT_PUBLIC_SUPABASE_PUBLISHABLE_KEY` を使い、`@supabase/ssr` でブラウザ用とサーバー用のクライアントを分ける。サーバー用は `server-only` でブラウザに入らないようにする。Supabase CLI は devDependency に入れて `npx supabase` で揃える。フォントは外部取得をやめてシステムフォント。
- 理由: 環境差を減らすため。拾った人用ページを軽くするため。秘密の鍵をクライアントに混ぜないため。
- 代案と見送った理由: 旧来の anon key 名 → Supabase が publishable key へ移行中。Google Fonts → 日本語では効果が薄く、ビルド時に外部通信が要る。
- 補足: セッション更新用の `proxy.ts` はログイン（M2）で追加する。D-002 の構成で雛形を作成済み。

### D-004: 開発の進め方は .claude/ のエージェント分担で行う（2026-11-27）
- 状態: 確定
- 判断: architect / developer / tester / reviewer / scheduler の5役と、`/morning` `/plan` `/build` `/status` `/review` `/checkpoint` `/parallel` のコマンドで進める。タスクは `.claude/tasks/` に1タスク1ファイル。
- 理由: 1人開発でも設計・テスト・レビューを飛ばさないため。セッションをまたいで状態を引き継ぐため。
- 代案と見送った理由: 外部のタスク管理ツール → リポジトリ内で完結させたほうがエージェントが読み書きしやすい。

### D-003: タグにはランダムIDのURLだけを書く（2026-11-27）
- 状態: 確定（設計書 v0.1 §4・§5）
- 判断: タグとQRには `https://（ドメイン）/t/（推測できないランダムID）` だけを入れ、書き込み後にロックする。個人情報は書かない。会話はサーバーで中継し、お互いの連絡先は見せない。
- 理由: 拾った人に悪意があっても漏れる情報を最小にするため。
- 代案と見送った理由: 連番ID → 総当たりで他人のタグを探せる。

### D-002: 技術構成は Next.js ＋ Supabase を推奨（2026-11-27）
- 状態: 提案（ユーザー未確定）
- 判断: 画面は Next.js（App Router, TypeScript）、データ・認証・写真は Supabase。通知はメールから始め、LINE は後。
- 理由: 1人で認証・DB・ストレージまで早く作れる。会話・通報のような関係データは Postgres が扱いやすい。
- 代案と見送った理由: Firebase（関係データが扱いにくい）、Cloudflare Workers ＋ D1（認証を自前で組む部分が多い）。
- 要確認: Supabase の東京リージョンと料金。

### D-001: 最初の対象は「持ち物」、配布ルートは学校・イベント（2026-11-27）
